# 对照阅读：Word 中英文对照加载项

这个加载项在 Word 右侧打开一个窗格。你可以在窗格里导入另一个 Word 文件（.docx），比如正文是英文稿，导入的是中文稿。加载项会找出两份文件中相互对应的标题、“摘要 / Abstract”一类的章节名称和图表题注，用它们把两份文件对齐。打开“同步滚动”开关后，滚动左边的正文，右边会跟到对应的位置；滚动右边，正文也会跟过去。

导入的文件只在本机解析，不会上传到任何地方。加载项也不会修改正在编辑的文档。

## 一、安装（只需做一次）

Word 加载项的界面是一组网页文件。Word 要求这些文件放在一个 HTTPS 地址上，所以安装分两步：先把文件放到 GitHub Pages，再让 Word 知道这个地址。

**第一步：把文件放到 GitHub Pages。**

1. 在 GitHub 新建一个公开仓库，名字建议用 `word-parallel-reader`。
2. 在仓库页面选择 “Add file → Upload files”，把本文件夹里的全部内容拖进去，然后提交。`test` 文件夹可以不上传，它只用于开发测试。
3. 打开仓库的 Settings → Pages，在 “Build and deployment” 中把 Source 设为 “Deploy from a branch”，分支选 `main`，目录选 `/ (root)`，保存。
4. 等一两分钟，浏览器打开 `https://你的用户名.github.io/word-parallel-reader/taskpane.html`。如果能看到“导入对照文档”按钮和“当前不在 Word 中”的提示，说明托管成功。

**第二步：生成 manifest 并装进 Word。**

manifest 是一个 XML 文件，告诉 Word 加载项的网页在哪里。在终端里进入本文件夹，运行下面的命令（把“你的用户名”换成你的 GitHub 用户名）：

```bash
node scripts/make-manifest.js https://你的用户名.github.io/word-parallel-reader
mkdir -p ~/Library/Containers/com.microsoft.Word/Data/Documents/wef
cp manifest.xml ~/Library/Containers/com.microsoft.Word/Data/Documents/wef/
```

第一行生成 `manifest.xml`，后两行把它放进 Mac 版 Word 读取加载项的文件夹。如果 macOS 询问终端是否可以访问其他应用的数据，选择允许。

然后完全退出 Word 再重新打开，打开任意文档，在“开始”选项卡点“加载项”，选择“对照阅读”。之后“开始”选项卡右侧会出现“对照阅读”按钮。

## 二、使用方法

点“对照阅读”按钮，右侧出现窗格。窗格默认比较窄，可以拖动窗格左边缘把它拉宽，对照阅读会舒服很多。

点“导入对照文档”选择 .docx 文件，也可以把文件直接拖进窗格。导入后，状态栏显示文件名、对齐上的标题和题注数量，以及段落一一对应的比例。下次在 Word 中打开同一份正文时，加载项会自动重新载入上次导入的文件。

“同步滚动”开关控制同步功能。打开时，两边一起滚动；关闭时，两边各自滚动，互不影响。

其他操作：

- 在左边正文里点击某一段，右边对应的段落会闪一下；如果它不在视野里，右边会滚过去。
- 双击右边任意一段，左边正文会跳到对应的位置。
- 右上角“⋯”菜单里有“匹配详情”，列出两边对上的标题，以及没对上的标题。点击其中一行，两边会同时跳过去。
- 同一菜单里可以调整右侧字号、重新匹配，或移除对照文档。

右侧标题左边的短竖条表示匹配状态：蓝色表示在正文中找到了对应标题，灰色表示没有找到，橙色表示当前所在的章节。

## 三、两份文件是怎样对齐的

对齐分两层。

第一层是“锚点”，也就是两份文件中可以确定相互对应的位置。加载项把以下几类段落当作候选锚点：使用了标题样式或设置了大纲级别的段落；以“一、”“（二）”“1.2”“第三章”这类编号开头的短段落；整段加粗的短段落；“摘要：”“关键词：”开头的段落；以及“图 1”“Figure 1”“表 2”“Table 2”开头的题注。然后，加载项用三条线索判断两边的候选锚点是否对应：章节名称是否属于同一类（例如“引言”与“Introduction”，“研究方法”与“Methods”，“参考文献”与“References”）；编号换算后是否相同（例如“三、”下的“（二）”与“3.2”）；以及它们在各自文档中的相对位置和标题级别。匹配必须保持前后顺序，所以一处误判不会打乱整篇的对应关系。只在一边出现的章节（例如英文稿的“Funding”）会保持未匹配。

第二层是锚点之间的段落。翻译稿通常按段落对应，所以加载项在相邻两个锚点之间，按段落长度把两边的段落配对。配对允许一段对两段、两段对一段，以及某一段只在一边出现。这一步让同步在长章节内部也能对得上，而不只是在标题处对齐。

## 四、精度和限制

**Word 版本。** 滚动同步需要 Word for Mac 16.100 或更新的版本（Windows 版需要 2508 或更新的版本）。从这个版本起，Word 才允许加载项读取和设置正文的滚动位置。版本更低时，加载项会自动改用“光标跟随”模式：你在正文中点击或移动光标，右侧才会跟上；滚动右侧不会带动正文。状态栏会显示当前处在哪种模式。

**滚动精度。** 按微软的接口文档和以往 VBA 中同名属性的行为，Word 告诉加载项的滚动位置很可能只是一个整数百分比。加载项会结合 Word 报告的“当前可见的页”和每页的内容，推算窗口顶部对应哪一段。在模拟的 Word 排版上测试时，推算误差平均约 0.03 页；在真实的 Word 中误差是多少，需要实际使用后才能确认。另外，文档越长，1% 代表的距离越长，所以在长文档里，右侧会一小段一小段地跟随，而不是逐行跟随。需要精确对照某一段时，在左边点击那一段即可，右侧会直接标出对应段落。如果加载项发现 Word 给出的是带小数的百分比，会自动改用更精细的推算。

**右侧的显示效果。** 右侧窗格把 .docx 转成网页来显示，保留标题、段落、列表、表格、图片、脚注和尾注，但不保留精确的版式和字体。Word 公式不会显示。批注不显示。修订按“全部接受”之后的样子显示。文本框的内容显示在它所在段落的后面。旧版 .doc 文件需要先在 Word 中另存为 .docx。

**位置推算的假设。** 加载项根据字号、行距和图片高度估算每段在页面上的位置。浮动在文字上方的图片、多栏排版、并排显示多页这几种情况，估算会比较粗。

## 五、更新和故障排除

如果更新了 GitHub 上的文件，而 Word 里还是旧版本，可以在窗格右上角的加载项菜单中选择 “Clear Web Cache”，然后关闭并重新打开窗格。

如果加载项从“加载项”菜单中消失，重新执行上面第二步的 `cp` 命令，再重启 Word。

如果要彻底清除 Office 的加载项缓存，可以在终端运行 `npx office-addin-cache clear`。这条命令会移除所有侧载的加载项，之后需要重新执行第二步。

## 六、文件说明

| 文件 | 作用 |
|---|---|
| `taskpane.html` / `taskpane.css` | 窗格界面 |
| `src/taskpane.js` | 读取正文、渲染对照文档、同步滚动 |
| `src/align.js` | 锚点识别与对齐算法，不依赖 Word，可单独测试 |
| `commands.html` | 功能区按钮需要的空白页面 |
| `vendor/` | 第三方库：mammoth（docx 转网页，BSD-2 许可）与 fflate（解压 docx，MIT 许可） |
| `assets/` | 功能区图标 |
| `manifest.template.xml`、`scripts/make-manifest.js` | 生成 manifest |
| `test/` | 单元测试和浏览器测试（使用模拟的 Word），不需要上传 |

## 七、开发与测试

`node --test test/align.test.js` 运行对齐算法的单元测试。

`python3 test/make_fixtures.py` 生成测试用的中英文 docx；`python3 test/make_mock_model.py 输入.docx 输出.json` 把 docx 转成模拟 Word 读取到的段落数据；`python3 test/run_browser_tests.py` 在无头 Chrome 中用模拟的 Word 测试导入、匹配、双向滚动、开关，以及部分接口缺失时的降级。这些测试需要 python-docx、Pillow 和 Playwright。

模拟的 Word 只是按行数排版的近似模型。它验证的是加载项的逻辑，不能代替在真实 Word 中的测试。
